# The node

The miner was a thought. It is not needed. A verifying node is the piece worth placing, and only where it is the best tool for that job.

This page asks that question of every branch under SpaceX and Tesla. High-frequency programmable proof of work means about ten blocks a second, a script every full node checks, and no vendor in the middle. It is the best tool when the job is to order a small statement that was already fit to publish, and to let the parties check it without an account at the company. It is the wrong tool when a machine, a beam, a market, or a secret already has a better channel. Those channels stay.

Nothing here is for sale. No company is claimed to be doing this. No one is asked to send KAS.

Press in November 2026 describes Tesla as Nasdaq `TSLA` and Space Exploration Technologies as Nasdaq `SPCX`. This page does not take a share price from those reports. The point that matters is the one a public company already lives with: a small repeatable cost is visible, and so is a small repeatable saving. This page does not convert either into dollars. Where Kaspa would be a second system beside a tool that already works, the cost goes up. Where it replaces a vendor who was the only copy of a row the parties already keep, the cost can go down. Both sentences are unread until someone measures them.

## The lenses

**Security.** The node checks that a hash was ordered and that a script was satisfied. It does not authenticate a vehicle command, a beam, a contactor, or a dispatch instruction. Those keep the keys they already have. A customer who wants that check on their own premises runs the node behind their own firewall, on mainnet. The section "Firewall, testnet, mainnet" is that placement.

**Efficiency.** The chain is fast so one seal lands in a fraction of a second. It is not an invitation to stream sensors. One transaction per published note, or per interval the parties already store, is the efficient use. A sample every millisecond is the expensive one, and it does not fit the block.

**Transparency.** Anyone with the file and a node can recompute the hash and compare it to the seal. Anyone without the file learns only the hash. A later edit of a website does not inherit the old digest.

**Permissionless.** There is no Kaspa account to open and no office to approve the broadcast. Paying the fee and meeting the script is the whole admission.

**Censorship resistance.** No office can phone the chain off, and no office can delete an ordered hash. A pool can leave a transaction out of the blocks that pool builds. Another miner can still include it. That delay is not the chain stopping. A default node shows the transaction inside the pruning window, 108_000 seconds in rusty-kaspa v2.1.0, and not by that call after it. The file is not in the 81 bytes.

**Free to use.** There is no vendor and no contract. The relay fee is still 100 sompi per gram. The node is still the operator's computer: the Toccata guide asks for at least 8 cores, 16 GB of memory, a 640 GB SSD, and on the order of 80 Mbit/s ([that guide](https://github.com/kaspanet/rusty-kaspa/blob/master/docs/toccata-guide.md)). The consensus pin of this study stays v2.1.0. Free of a landlord is not free of electricity.

**Economics.** For a public company the fee on one seal is the small number. The node is a larger number, and it is paid once by whoever wants the local copy. A ground node next to the reader is the cheap placement. A node on a spacecraft is justified only when that vehicle is the reader and the ground site is the failure. A miner is neither the security nor the saving.

## Where it is the best fit

Four jobs, and then stop.

1. **A meter interval the parties already keep.** Energy. The electrons have flowed. The dispute is which row was the row. The node sits with the site, the aggregator, and the offtaker.
2. **A passport or packing extract the next holder cannot fetch from one portal.** Supply chain. The node sits with the recycler, the supplier, or the shop that lost the vendor's site.
3. **A document that was published on purpose.** A launch note, a Starlink status, a system card, a charging receipt, an inspection pack. The node sits with the reader who may lose the website. One seal per publication, not per sensor.
4. **A reader that is already in space and already has broadband.** A Starlink terminal that is up, or a Starmind computer if one is flying, or a ship that stays on orbit. The node checks the seals in the three jobs above. It does not run the vehicle.

A KAS covenant is a fifth job only when both sides want KAS. The example is [`seal_escrow.sil`](code/covenant/seal_escrow.sil). It is optional. The dollar draft in [DOLLAR.md](DOLLAR.md) is not required for any of the four, and it is not a coin yet.

## Launch

**Best tool.** The range, the license, and the flight computer. Kaspa does not fly the vehicle.

**Where the node wins.** A telemetry snapshot, a mishap update, or a manual that was already published.

**What.** Seal the file. The parties who care run a node, or use any node they can reach. A ship that remains on orbit and already has a broadband path can run one pre-synced node so the vehicle can check the digest without a ground website.

**Why.** Security here is integrity of the published note, not of guidance. Transparency is the point of publishing it. Permissionless means a researcher needs no SpaceX account to check the bytes they were handed. Censorship resistance means a later edit of the site does not rewrite the old digest. Efficiency is one transaction per note. Economics is that fee, plus a ground node. A node on a ten-minute booster flight does not pay for itself. The seal can be broadcast from the ground before liftoff.

**How.** `seal_file(Branch::Launch, Kind::PublicFile, note)` produces the 81 bytes. The hash of the file is bytes 17..49. The version-1 id commits to the payload. The native subnetwork orders it. The node compares the file it was given with those bytes. Trajectory, guidance, and export-controlled drawings are not the file.

## Starlink

**Best tool.** The radio, the account, and the billing relationship. Kaspa does not point a phased array or grant a cell.

**Where the node wins.** A status or capacity figure SpaceX has already published. And, separately, a node behind a terminal that is already up, used as a reader of any seal in this study. Low orbit is a few milliseconds of vacuum delay. The chain's block interval is a tenth of a second. That reader can be a normal peer if the terminal can carry on the order of 80 Mbit/s.

**Why.** The constellation is the efficient way to move the company's own bits. Adding Kaspa to that path would be a second network. The efficient Kaspa use is the opposite: one hash of a statement the company chose to show, checked by anyone, including a terminal that can no longer open the website. Free to use means no contract with Kaspa. The Starlink subscription is still SpaceX's price. Economics: do not put the subscriber bill on the chain in order to save a card fee. A card or the company's own checkout is the better payment tool until both sides already want KAS.

**How.** `Branch::Starlink`, `Kind::PublicStatus`, on the published text. The node recomputes the hash. Subscriber locations and card numbers stay off the payload. The satellite becomes a Kaspa node only if the software and the disk are actually there. Being in space is not enough.

## Starshield

**Best tool.** A contract with a state, and an operator that state can direct. That customer wants a switch.

**Kaspa loses.** A chain with no office is the property this customer is not buying. A node does not make a government constellation permissionless, and it should not. No seal of tasking. No node as a back door around the operator. There is no efficiency gain in a second ledger for a network whose product is control. Stop.

## Starmind

**Best tool.** The orbital computer, if it flies: power, heat, radiation, laser links, launch mass. Nothing is flying under this page's evidence. Kaspa does not reject heat and does not run the job.

**Where the node wins.** As a passenger reader on that computer, if the computer already has power and a link, so a job receipt can be checked when the ground gateway is down. The receipt itself is the same publication seal as everywhere else: "request id H was accepted," "result digest R was published." The prompt stays off the chain.

**Why.** The customer's work is the efficient use of the radiator. A miner was considered as a heat load and dropped. A node is a smaller, steadier reason to spend a little of that power: a local copy of the chain, censorship resistant in the narrow sense that a blocked website is not the only place the receipt can be read. Permissionless applies to whoever can reach the node. It does not apply to the orbital computer, which has an owner. Economics: the node is justified only as a reader of receipts the mission already creates. It is not justified as a product line.

**How.** `Branch::Starmind`, `Kind::Receipt`, on the receipt text, not on the weights and not on the prompt. Native subnetwork. No user lane until a prover exists. vProgs had no release on this pass. The hash is the how, until a tag exists.

## Starbase and the factories

**Best tool.** The factory's own test system, the customs process, and the bank. A chain does not open a crate.

**Where the node wins.** An inspection pack or a shipment certificate when one vendor's portal is the only reader, and the other party already holds the file.

**Why.** The efficiency is the second copy of a record, not a faster weld. Transparency is two companies looking at the same hash. Security is that neither company's website is the judge of which PDF was the PDF. Economics: one seal per pack is a small fee. A node at each company that already stores the PDF is the placement. A node in the rocket is not the placement. If the portal is not a single point of failure, the existing files are enough and Kaspa is an extra system.

**How.** `Branch::Starbase`, `Kind::Inspection`, on the pack bytes the parties stored. Drawings that are export-controlled are not the pack. The node checks bytes 17..49. Customs still decides whether the crate moves.

## Terafab

**Best tool.** The manufacturing execution system inside the building. Recipes, yields, and tool logs are secret or export-controlled. They do not go on a public chain. That is the efficient choice and the lawful one.

**Where the node wins.** A public acceptance record, the same shape as the factory pack, if the counterparties are already allowed to hold it.

**Why.** Putting the process on Kaspa would be a cost and a leak, not a saving. A public company does not buy that. The acceptance hash is the only transparent object. Permissionless checking applies to that object only.

**How.** `Branch::Terafab`, `Kind::Inspection`, on the acceptance file. The eight-to-one power sentence from the space-watts post is not a recipe and is not sealed as one. The fab figures named elsewhere on that page are not verified here and are the wrong size for a covenant.

## xAI

**Best tool.** The API account and the cluster's own power contract. A government order served on the company still closes a key. Kaspa must not be a side door around that order.

**Where the node wins.** A system card, an eval, or a data statement the lab published. Researchers who cannot open the site can be handed the file and check it on any node.

**Why.** The training run is more efficient on the cluster than on a blockDAG, by an absurd margin. The published claim about the run is the opposite problem: it is small, and it gets edited. Transparency and censorship resistance apply to the claim. They do not apply to the prompts. Economics: one seal per publication. A node in the lab and a node with the outside reader. No node as a way to keep a banned customer on the model.

**How.** `Branch::Xai`, `Kind::Eval`, on the published file. The weight file, if it is already public the way grok-1 is, can use the same call. A private weight file cannot.

## X

**Best tool.** X's own servers for the feed, the ads, the accounts, and the chat. Community Notes already has a public algorithm and a writing process. X Money, on the product page read for this study, is a balance at a bank. A free in-app transfer is a better price than a chain fee for a transfer the product already calls free.

**Where the node wins.** Almost nowhere on this branch. A published snapshot of an open-source ranking file can be sealed the same way as any other release. That is a software-integrity habit, not a reason to sequence the product on Kaspa.

**Why.** The feed is high frequency in the ordinary sense, and Kaspa's high frequency does not make it a better host. Censorship resistance for speech is the company's product and the company's legal problem. A hash does not host a post. Economics: adding a chain under the feed adds cost and does not cut the bank, the card, or the moderation desk.

**How.** Do not. If a release tarball is already public, `Kind::PublicFile` on that tarball, and stop. Chat plaintext, ad auctions, and X Money balances stay off.

## Vehicles

**Best tool.** [vehicle-command](https://github.com/teslamotors/vehicle-command) and the key in the car. Telemetry goes to the server the owner or the fleet chose. The car does not ask a chain what to do. That is the efficient and the safe design.

**Where the node wins.** A recall note or a software-version note Tesla has already published. Not the car.

**Why.** A node in the vehicle would be a second computer on a safety path, which is a cost, not a cut. Permissionless checking of a public recall is useful to an owner who saved the PDF. Censorship resistance does not steer. Economics: the command protocol is already paid for. Kaspa does not undercut it.

**How.** `Branch::Vehicles`, `Kind::PublicFile`, on the published note. Dashcam, location, and door commands are not inputs. The car keeps its keychain.

## Energy

**Best tool for the watt and the market.** The breaker, the interconnect, and the ISO. nempy is a model of a market an operator already runs. Kaspa does not bid, and it does not keep a battery online.

**Where the node wins.** This is the strongest fit in the set. The parties already store an interval row: site, time, import, export. Each of them runs a node, or shares one they trust for the download and check themselves. The seal is the order of that row.

**What.** Hash the row. Seal the hash. Keep the row. Later, any of the three can show the row that matches the seal.

**Why.** Security is the integrity of the record after the electrons are gone. Transparency is three parties and the same bytes. Permissionless means the offtaker does not need an account in the aggregator's cloud to check a row they already hold. Censorship resistance means closing the aggregator's tenant does not rewrite the sealed intervals. Efficiency is one transaction per agreed interval, not per cycle of the meter. A national stream does not fit. Economics: the fee is the mass rate on that one transaction. The nodes are three copies of a computer the parties may already be willing to run, because they already keep the row. A public company's cost cut, if it exists, is the hosted database no longer being the only copy. This page does not price that saving. The ISO still clears in the ISO's unit. A KAS side agreement is optional and only between parties who want KAS. The dollar draft does not bid the market.

**How.** `Branch::Energy`, `Kind::Receipt`, on the row bytes. The row is not the payload. A dispatch instruction that is already public can be `Kind::PublicStatus`, and the instruction itself still moves on the utility's channel, which is faster and already authenticated. The script in this repository can lock KAS against the row hash. It checks one input, trusts an arbiter, and has no refund. Use it only when that shape is what the two parties asked for.

## Optimus

**Best tool.** The robot's own safety system, local logs, and a fleet cloud the company can pause. Video of workers and homes is the reason a public chain is the wrong archive.

**Kaspa loses.** A node does not make a log censorship resistant in a way anyone should want. Publishing the log to keep it would harm the people in the frame. There is no efficiency in a second ledger for a command that can hurt someone. Stop. A published spec sheet, already public, can be sealed like any other PDF. This branch does not need its own practice for that.

## Charging

**Best tool.** The stall's contactor, the site operator, and the payment token the driver already has: Tesla account, card, or roaming partner. The contactor is not a transaction output.

**Where the node wins.** The session receipt, after the session, when the driver and the site both keep the row and either one might later face a closed roaming hub.

**Why.** The efficient payment is the one the stall already uses. Kaspa does not cut that cost by sitting in the authorization path, and a node in the stall is a piece of hardware the charger does not need in order to close. Transparency of the receipt is the useful leftover: energy, time, site, token id if it is already on the receipt the driver holds. Censorship resistance applies to that receipt, not to the right to draw current. Economics: one seal per session is only worth it where the roaming record is a known single copy. Otherwise it is an extra fee on a solved problem.

**How.** `Branch::Charging`, `Kind::Receipt`, on the receipt bytes. The node runs with the driver or the site if they want the check. It does not sit in front of the contactor.

## Supply chain

**Best tool for the goods and the law.** The manufacturer's duty, customs, and the bank. A sanction is not a missing opcode. Kaspa does not certify a mineral.

**Where the node wins.** The second strongest fit. A packing list or a battery-passport extract the next holder is allowed to have, sealed so a dead vendor portal is not the only way to show it.

**Why.** The recycler, the shop, or the supplier in another country is the reader. A node there is permissionless in the practical sense: no account at the passport vendor. Transparency is the extract, not the secret process. Censorship resistance is a closed region on the vendor's site. Efficiency is one hash per extract the parties already store, against the cost of being unable to show it. Economics: that fee is small next to a stranded pack. It is not a new compliance regime, and it does not cut the cost of the legal duty. The manufacturer still owes the record.

**How.** `Branch::Supply`, `Kind::PassportExtract`, on the extract. The node checks bytes 17..49 against the file the holder kept. Counterfeit serials in a database this hash never saw are still counterfeit. The chain did not see them.

## Compute

**Best tool.** The cluster, the power contract, and [TTPoE](https://github.com/teslamotors/ttpoe) on the rack. Time on that fabric belongs next to Precision Time Protocol. Gradients and datasets stay off the chain. They are the asset, and they do not fit.

**Where the node wins.** The same publication seal as xAI: a system card or a power statement the lab chose to publish. A node with a reader who cannot open the corporate site.

**Why.** High frequency on the chain is not high bandwidth on the fabric. Using Kaspa for the frames would be less efficient by orders of magnitude. Using it for the published claim is the efficient slice. Security of the claim is the hash. Security of the building is still the building. Economics: one transaction per card. A node in orbit does not train the model. If the training moves to a Starmind computer, the node question moves with the receipt, which is the Starmind section, not a second compute design.

**How.** `Branch::Compute`, `Kind::Eval`, on the card. KIP-16 can check two proof tags. A training proof is not those tags. vProgs has no release. The PDF hash is the call that exists.

## Neuralink and The Boring Company

**Neuralink. Best tool.** The clinical system and the medical-device rules. A node does not belong. A public chain is a harmful archive for neural recordings, trial files, and firmware that is not already a public release note. No efficiency, no transparency gain worth the exposure, no economic case. Stop.

**Boring Company. Best tool.** The permit, the city, and the contractor's own files.

**Where the node wins.** Only the inspection-pack case already described for Starbase, and only when a single portal holds the only copy. A tunnel is not a space-watts problem and does not get a node because a rocket does.

**How.** The Starbase call, on a pack the parties already store. The permit stays with the city.

## Firewall, testnet, mainnet

A customer can follow the chain without mining. That is the whole of the security option. The node sits on their side of the firewall. It opens outbound connections to mainnet peers and does not invite the internet in. The file stays on their disk. The 81-byte seal is the only thing that becomes public, and only when they choose to broadcast it. This is reasonable for every job this page already calls a fit. It does not require a second chain.

**Mainnet is the record.** The public miners are there. A seal on mainnet is what a later reader can check, inside the pruning window, on any node that kept the transaction. The fee is real KAS, at the mass rate. Use it when the file was already fit to publish and the parties want that order. Do not put a secret in the payload. The firewall hides the file and the disk. It does not hide a transaction after it is broadcast. The hash, the branch byte, and the kind byte are then on the public chain.

**Testnet is the dry run.** It is reasonable for proving that the encoder bytes match, and for learning the wallet errors, and then stopping. This repository already has that note. A local TN10 node at server version 2.1.0 built an 81-byte seal and did not return a txid. No transaction was broadcast. Testnet can be reset. It has no lasting public weight. It is not the archive a supplier, a recycler, or a launch note should rely on. The Kaspa Dollar draft names its own testnet in May 2027. That is a different project and it is not this seal.

**A chain the customer floats is not reasonable.** A private fork, a firewalled network with no path to mainnet, or a chain whose only miners are the customer's, is a database with extra steps. Outsiders cannot check it without the customer's permission, which is the opposite of the permissionless lens. It has no public hashrate, so it has no censorship resistance of the kind this study means. If the security need is that nobody outside may learn that a document exists, do not seal it. Keep the file inside. Kaspa cannot be the public clock and a private network at the same time.

**Coming and going has a limit.** A node that follows the tip only when the customer turns it on can check a fresh seal. A default node that has been off longer than the pruning window, 108_000 seconds in v2.1.0, cannot produce the old proof from its own data. The call returns `BlockTooDeep`. An archival node, or a witness saved while the block was still available, is the way to keep the older check. That is a disk choice. It is not a second network.

## What this page does not do

It does not send a miner. It does not put every branch on Kaspa. It does not estimate a saving for `TSLA` or `SPCX`. It does not fly a node. It does not start a node, and it does not broadcast. It does not ask anyone to send KAS.
